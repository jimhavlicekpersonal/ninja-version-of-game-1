# Device/network compatibility audit — Kagemura client runtime (read-only, 2026-11-05)

Method: read index.html, main.ts, app.ts, pwa/*, render/{quality,assets,fx,VillageScene,BattleScene,touchInput,fonts,artManifest}.ts, persist/idb.ts + saveStore.ts, audio/sound.ts, platform/*, net timeouts, styles.css, vite/capacitor configs, android/ and ios/ projects, tools/perf; ran `npm run build` once (dist sizes below) and one scratch vitest measurement (scratch dir only; repo untouched). No device was available; "VERIFIED" means read in current code or computed from it.

**Built sizes (vite 8.3.5):** `assets/index-*.js` 1,476,756 B raw / 415 KB gzip -9 (one bundle, no code splitting; only 3 tiny Capacitor `web-*.js` chunks), CSS 50 KB / 12 KB gz, fonts 48 KB, `index.html` 16 KB / 5.7 KB gz (the full commented boot.js is inlined unminified), `sw.js` 7.5 KB, icons 344 KB. First visit over the wire ≈ 480 KB; service-worker install then adds the non-hashed files (≈ 400 KB, see F7). GitHub Pages serves gzip only (no brotli).

## Findings

**F1 — High — Per-level building textures are never evicted: texture memory grows all session (VERIFIED)**
`src/presentation/render/assets.ts:120-146` (`buildingTexture` → `paintLevel`) paints one texture per `type × level` on first use and keeps both the GPU copy and the CPU canvas (`paintingCanvas`, `willReadFrequently: true`, kept on purpose for thumbnails/hit tests). Nothing ever calls `textures.remove` (grep: no removals in render/). Scouting rivals at other Keeps, replays, Trials, Gang Wars, Build-menu thumbnails (`buildingThumbKey` paints level 1 of every shop type) and Keep skins (`hallSkinLevel`) all add textures. Scratch measurement from `buildings.json` + painter `extra` heights: 276 type×level looks = **208 MB on `high` (2.5x) / 75 MB on `low` (1.5x)** GPU alone, ×2 with the kept canvases, on top of the 36.6 MB (high) / 16.3 MB (low) island (4080×2241 / 2720×1494 px, each also kept as a canvas). The audit's "62 MB high / 26 MB low" is a first-frame figure only. On a 2 GB Android Go phone the WebView renderer is killed around 0.5 GB; on iOS Safari the per-page canvas budget silently returns blank canvases once exceeded, so late-session buildings would paint as nothing. Suggest: an LRU on `Keys.buildingLevel` textures (evict on `scene.sleep`/battle end, keep the current village's levels), release the painting canvas after upload except for the few keys that need `getBase64`, and cap total painted bytes per profile.

**F2 — High — Auto quality picks `high` for any phone with ≥ 6 GB RAM regardless of GPU, and the canvas benchmark never runs on Chrome (VERIFIED)**
`quality.ts:117-133`: with `deviceMemory` present (every Chrome/WebView), the decision is memory-only (`≤3` low, `4 + touch` low, else high) and `readSignals()` skips `measureFillMs` (`fillMs: deviceMemory === undefined ? … : undefined`). Cheap 6–8 GB phones with Mali-G52/Adreno 610 class GPUs and 1080×2400 DPR-2.6–3 screens get a 3x canvas (1080×2400 framebuffer), 2.5x/3x textures, `powerPreference: 'high-performance'`, 60 FPS target and 6–7 full-screen alpha-blended parallax layers (F10). There is also no run-time downgrade: a profile is fixed for the session (`quality()` memoised) even if frames drop or a WebGL context is lost. On iOS, iPhone X/XS/11 (3–4 GB, iOS 15, DPR 3) are "high" by the home-button rule. Suggest: run the fill benchmark always; add a screen-pixel budget (`screenShort × screenLong × DPR²`), treat DPR ≥ 2.5 + `coarsePointer` as "cap canvas at 2x" independent of memory; measure `actualFps` over the first 20 s and persist a downgrade.

**F3 — High — The 25 s "taking a long time" card wipes the progress line and offers a Retry that restarts a nearly-finished boot (VERIFIED)**
`boot.js:191-213` `show('slow')` removes every child of `#boot`, so `main.ts bootStatus()` (`querySelector('#boot .boot-status')`) silently stops updating; the timer (`SLOW_MS = 25000`) starts at HTML parse and is never reset when the module arrives (`__tkStarted` only suppresses error cards). Arithmetic for the audit's own "2G/EDGE, cheap phone" profile (`tools/perf/lowend.mjs`: 240 kbps, CPU×6): 415 KB gz ≈ 14 s download + CSS/fonts + IDB open + texture painting (audit: 4.5 s high / 2.4 s low longest task, total painting several seconds) → the card appears while painting is at 70–90 %. Retry calls `location.reload()` → start over → same card: a loop on exactly the devices this is for. Suggest: `__tkBoot.progress(text)` from main.ts that resets/extends the timer; keep the status line under the card; show "Retry" only when no progress has been reported for N s.

**F4 — Medium — Every launch on a slow network waits 3.5 s for the network before the cached shell is used (VERIFIED)**
`sw.template.js:150-178` `navigate()`: network-first with `NAV_TIMEOUT_MS = 3500`; when online but slow, each cold launch adds up to 3.5 s before the cached `index.html` is served, and the network response is then discarded (never written over the shell, by design) so the bytes are wasted; on a flaky link the `fetch` can also hang up to the timeout. Suggest: cache-first for navigations when a complete cache exists, with `registration.update()` doing the version check (it already does, `register.ts`), or a 1 s timeout.

**F5 — Medium — Service-worker install re-downloads ≈ 400 KB of non-hashed files per build, including two 512-px icons the page never uses (VERIFIED)**
`cacheModeFor` (`sw.template.js:34`) uses `'reload'` for everything outside `/assets/`: `icons/icon-512.png` 149 KB, `icon-maskable-512.png` 139 KB, `apple-touch-icon` 27 KB, five legal pages ≈ 60 KB, `manifest`, `legal.*`. Only `/assets/` is deduplicated through the HTTP cache (the audit's "downloaded once" fix covers hashed files only). On 2G that is another ~15 s of transfer per update, during play (registration happens after the first frame). Suggest: fingerprint public files or compare `ETag`/`content-length` before refetch; drop the 512-px PNGs from the precache (only needed by the OS at install time), or shrink them (149 KB for a 512² PNG is unoptimised).

**F6 — Medium — The iOS "keep it safe" advice sends players to a Home Screen app with a different, empty storage (VERIFIED text; behaviour per iOS storage partitioning)**
`main.ts:396-401` `persistNote` on iOS: "add Kagemura to your Home Screen … and play from there". On iOS, a Home Screen web app has its own WKWebView data store, separate from Safari's IndexedDB, so the Home Screen copy starts a new village; the existing one stays in Safari where the 7-day eviction still applies. The save-code and sign-in alternatives are listed after it. Suggest: on iOS say "copy a save code first, then add to Home Screen and load it there" (or link a sign-in), and detect `display-mode: standalone` to offer "Load from code" on an empty village.

**F7 — Medium — Render-blocking CSS gates the splash; module script precedes the stylesheet (VERIFIED)**
Built `dist/index.html:353-354`: `<script type="module" crossorigin src=assets/index-*.js>` then `<link rel="stylesheet">`. The `#boot` layout (`styles.css:91-101`: `position: fixed; inset: 0; display: grid …`) lives only in the 12 KB gz stylesheet, so the page is blank (white, unstyled `<img>` + text if the CSS fails) until the CSS arrives; `boot.js bootEl()` inlines styles only for error cards. On 2G that is 1–3 s of nothing before the "lanterns" splash. Suggest: inline the ~8 `#boot` rules in `index.html`, mark the module `fetchpriority`/`modulepreload`, and minify the inlined boot.js (16 KB with comments → ~4 KB).

**F8 — Medium — fx.ts uses `textures.createCanvas` for the scenery and ruins, the exact pattern the re-audit said was removed (VERIFIED)**
`fx.ts:147-160` `artTexture()` → `scene.textures.createCanvas` for `scenery.ridge.{0,1,2}` (1600×300 each at res 1 on high), `scenery.fog`, `rubble.<size>.<family>` (4 sizes × 4 families at `BUILDING_SCALE` 2.5x, painted during battles), `fx.bird`, `fx.streamer`, `fx.villager.0-3`, `fx.cloudshadow`, `fx.petal`. Each `CanvasTexture` keeps the `ImageData` copy the audit's item 14 removed elsewhere (assets.ts comment 221-227). Scenery "5.9 MB on high" is therefore ~3× that in RAM. Suggest: route `artTexture` through `canvasFor`/`addPainted`.

**F9 — Medium — Background music is synthesised and scheduled even when the player muted it (VERIFIED)**
`sound.ts:394-437`: `music()` starts a 100 ms `setInterval`; `scheduleMusic()` creates oscillators/buffer sources for drones, plucks and taiko every eighth note (84/128 BPM) with no check of `this.settings.music` — muting only sets `musicGain` to 0, so the audio thread keeps rendering a silent track for the whole session (CPU + battery on a cheap phone; the village idle throttle doesn't touch it). Suggest: stop the interval when music is off or the context is suspended; resume on unmute.

**F10 — Medium — Overdraw: 6–7 full-screen alpha layers on every frame, with no reduction in the `low` profile (SUSPECTED; counts VERIFIED)**
`fx.ts addScenery` (3 ridge images scaled ×2.0–2.6 of 1600×300 with scroll factors, 2 fog bands scaled ×7, each tweened), `assets.ts addSurroundings` (backdrop + 24–60 wisps), `VillageLife.cloudShadows` (128×64 images scaled 7×5 at alpha), plus the island. Low quality only halves ridge resolution (`res = 0.5`), not the layer count, so a 720×1600 `low` canvas still fills ≈ 8 Mpx/frame → 240 Mpx/s at 30 FPS, at the limit of Mali-400/T720-class GPUs. Suggest: on `low` drop to one ridge layer and one fog band, no cloud shadows, or pre-composite ridges+fog into one texture.

**F11 — Medium — Thumbnails: synchronous PNG encode of every shop building / all 50 warriors on first open, cached forever as base64 strings (VERIFIED)**
`main.ts:342-350` `thumbOf` → `game.textures.getBase64(key)` (canvas → `toDataURL`) stored in a `Map` for the session; `hud.ts:1417` calls it for every `inShop` type when Build opens (and `buildingThumbKey` first paints level-1 art for types not yet on the map); `hud.ts:1571` for every Codex row; `armyUi.ts:61`, `groveUi.ts:250/270`, `battleHud.ts:445` for troops. On a slow phone this is tens of main-thread PNG encodes (~5–20 ms each at 2–3x) on one tap, plus MBs of data-URL strings and decoded `<img>` bitmaps. Suggest: encode lazily per visible row (IntersectionObserver), use `canvas.toBlob` → object URLs (async, no base64), and draw thumbnails at 1x.

**F12 — Medium — Old Android WebView path: the app passes Capacitor's WebView ≥ 60 gate but the es2020 bundle needs ≥ 80, and the message tells users to update "Chrome" (VERIFIED)**
`capacitor.config.ts` sets no `android.minWebViewVersion` (Capacitor default 60, `Bridge.java:105`); `vite.config.ts build.target: 'es2020'` leaves optional chaining/`??` in the bundle (Chrome 80+). `boot.js missingFeatures()` catches it and says "Update your phone (iOS 15 or later) or your browser (Chrome, Safari, Edge or Firefox …)". Inside the Android app the fix is "Android System WebView" in Play (or the phone has no Play Services). Android 7 devices without Play updates ship WebView 51–58. Suggest: set `android.minWebViewVersion: 80` (Capacitor then shows its own update page) and word the guard's message for the app case (detect `window.Capacitor`).

**F13 — Medium — Canvas-renderer fallback would draw role rings, flashes, smoke and ruins untinted (SUSPECTED)**
`main.ts:301` `type: Phaser.AUTO` falls back to Canvas when WebGL is unavailable (blacklisted old GPUs/WebViews, or WebGL disabled). Phaser 3's Canvas renderer has no tint path (`renderer/canvas/CanvasRenderer.js` contains no tint code), while the game relies on `setTint` for troop role rings, muzzle flashes, death puffs, jam dimming, smoke lobes, confetti, villagers and the `FLASH`/`RING` white textures (`fx.ts:214,236,255`). Readability of battle (which rules depend on) would collapse to white shapes. Suggest: either refuse Canvas (`type: Phaser.WEBGL` + a "needs WebGL" card from the boot guard, which already probes `canvas.getContext`) or pre-tint the few role/flash textures.

**F14 — Low — Autosave serialises the whole village every 15 s with no dirty check, visible or not (VERIFIED)**
`main.ts:565` `setInterval(() => controller.save(), 15_000)`; `controller.ts:582-590` `persist()` always `serialize()`s and writes to IDB (structured clone + disk). Save size: new village 4.9 KB; each kept battle record carries a full `BattleSetup` (scratch: 5.8–7.5 KB per opponent base at Keeps 5–15), `maxReplays` 10 + `maxDefenseLog` 10 → ≈ 150–300 KB per write at late Keeps. Minor CPU/flash cost, but it runs in background tabs (throttled to 1/min) too. Suggest: a `changed` flag from `onCommand`, save on change + on hide/pagehide only.

**F15 — Low — `backupDamaged` backups accumulate without limit (VERIFIED)**
`saveStore.ts:118-120` writes a new `backup:<timestamp>` key on every damaged load and before every `restoreBackup` (`controller.ts:212, 556`); only manual `deleteBackup` removes them. A village stuck in a load→repair loop fills IndexedDB on a low-storage phone, and Android Auto Backup (which includes WebView IndexedDB per `backup_rules.xml`) silently stops above 25 MB. Suggest: keep the newest 3 backups.

**F16 — Low — `lazyTiers` is dead: the profile table advertises a difference that doesn't exist (VERIFIED)**
`assets.ts:248` takes `_lazyTiers` and ignores it; every profile paints per level on first use. Harmless, but `quality.ts` docs/Settings text ("generates building tier art only when shown" on low) and the audit's R03 row describe a non-existent saving. Suggest: delete the flag or make it mean something (e.g. F1's cap).

**F17 — Low — Fonts: boot serialises a 1.5 s font wait before Phaser starts; canvas text keeps fallbacks forever (VERIFIED)**
`main.ts:277` `await loadInterfaceFonts()` (`fonts.ts`, 1.5 s race) before `new Phaser.Game`; on 2G the 48 KB woff2 arrive later, so building timers / battle stamps are drawn in the fallback font for the session (acknowledged in fonts.ts). Suggest: start Phaser immediately and `textures`-independent text re-style on `document.fonts.ready`, or preload the two fonts with `<link rel=preload>`.

**F18 — Low — iOS app: Web Audio takes over the audio session on the first tap (VERIFIED: no `AVAudioSession` configuration in `ios/App/App/*.swift`; effect SUSPECTED)**
`sound.ts:58-81` creates the `AudioContext` on the first `pointerdown` even when both sfx and music are off. In WKWebView the default playback category pauses the user's music/podcast. Suggest: set `AVAudioSession` to `.ambient` in `AppDelegate`, and don't create the context until a sound is actually wanted.

**F19 — Low — No `android:largeHeap`/memory signals, and no handling of `onTrimMemory`/`memorywarning` (VERIFIED absence)**
Nothing in `MainActivity.java` or the web code listens for memory pressure; combined with F1 the renderer is killed rather than shedding textures. Suggest: a Capacitor plugin forwarding `onTrimMemory` (and iOS `didReceiveMemoryWarning`) to a `window` event that evicts F1's cache.

**F20 — Low — Reduced motion and `low` do not reduce the per-second object churn of village life (VERIFIED)**
`fx.ts VillageLife`: each smoke source creates and destroys an image + tween every 1.1–1.5 s (÷`particleScale`: 2.2–3 s on low), 4 walkers with per-frame `onUpdate` depth recomputation, 8 petals, 3 birds/7 s, glints with `repeatDelay`; `prefers-reduced-motion` only halves counts (`quality.ts:166`). On a 2 GB phone this is steady GC churn at the idle 20 FPS. Suggest: on `low`/reduced motion, pool puff sprites and stop walkers/petals.

**F21 — Low — Large-text accessibility: 61 `px` font sizes, zero `rem/em` (VERIFIED; R10 still open)**
`styles.css` (61 px sizes; `--rb*` sizes in px). Android Chrome's text scaling still boosts px text, but iOS Dynamic Type and WKWebView never do. Already listed as open in the audit; noting that nothing changed in code.

**F22 — Low — Boot error paths on iOS 15.0–15.3: `:has()` in CSS is ignored (cosmetic) and `inset`/`backdrop-filter` are fine; the polyfill set (structuredClone, `.at`, `Object.hasOwn`) matches actual usage (VERIFIED)**
Grep of src/ found no `findLast`, `AbortSignal.timeout`, `Promise.any/allSettled`, `WeakRef`, `OffscreenCanvas`, `ResizeObserver`, `BroadcastChannel`, `Intl.*` (names use pinned `unicode-segmenter`), `crypto.randomUUID` is guarded (`events.ts:100-104`), `navigator.storage`/`document.fonts`/`AbortController`/`Notification`/`vibrate`/`clipboard` are all guarded. No action; recorded so the claim is evidenced.

**F23 — Low — Notification permission timing is correct (VERIFIED)**
Both web (`reminders.ts enable()`) and native (`native.ts`, `push.ts pushDevice()`) prompt only after the player switches reminders on; `syncPush` (`connection.ts:242-260`) returns before touching `pushDevice` when no types are enabled. Android Back is wired (`main.ts:613-626`), `pagehide`/`visibilitychange` saves exist. No issue; only device verification remains.

## Claims in the prior audit that I could not confirm or that are wrong
- "Code art … added with `textures.addImage` … never `createCanvas`" — wrong for `render/fx.ts` (F8): ridges, fog, ruins, villagers, birds, petals and cloud shadows all use `createCanvas`.
- "`low` … generates building tier art only when a building at that tier is shown" — the flag is unused; both profiles paint per level on first use (F16). The real difference is scale only.
- "Textures 115.3 → 23.5 MB" / "~62 MB high, ~26 MB low" — first-frame figures. The island alone is 36.6 MB (high) / 16.3 MB (low) GPU plus the same again as a kept canvas, and nothing bounds growth over a session (F1).
- "SW downloaded everything twice → fixed" — fixed for `/assets/` only; ~400 KB of icons/legal pages are re-fetched with `cache: 'reload'` on every build (F5).
- "Auto quality: new rule + 2 ms canvas fill test" — the fill test never runs where `deviceMemory` exists (all Chrome/WebView), so on Android the rule is RAM-only (F2).
- "Splash until first frame, progress line" — true until 25 s; after that the guard replaces the progress line and offers a reload (F3).
- "Village idles at 20 FPS (CPU 102 % → 37 %)" — the frame loop does, but the music scheduler (F9), 15 s full serialisation (F14) and village-life tweens (F20) continue.
- "Safari 7-day eviction … 'Keep it safe' banner (Home Screen …)" — the Home Screen advice leads to a separate, empty storage on iOS (F6).
- R08 "16 KB safe, no native libraries in the added AARs" — plausible from `build.gradle` (no `.so` in the app; AGP 8.13); not verifiable here without the resolved dependency graph, as the audit itself says.
- Confirmed as described: boot guard + polyfills + feature check (`boot.js`), IDB 5 s timeout and reconnect (`idb.ts`), custom Phaser build (422 KB gz vs. full), page zoom allowed, inputs `max(16px,1em)`, Android Back, art-manifest deadline, store-price timeout, `maxReplays` 10 / `maxDefenseLog` 10, iOS 15 / minSdk 24 / target 36, exact-alarm permission removed, backup rules excluding localStorage.

## Big-picture assessment
The client-runtime pass is real: the boot guard, polyfills, IDB resilience, service-worker install rules, sliced texture painting and the two-profile renderer all exist and read as described, and the browser-API surface is genuinely iOS 15 / Chrome 80 safe. What remains is structural rather than a list of missing guards: texture memory is unbounded over a session (the one thing most likely to kill the game on a 2 GB phone or blank it on an iPhone), the profile chooser trusts RAM and never adapts at run time, and the whole game is one 1.5 MB bundle whose slow-network boot runs into its own 25 s guard. Several "fixed" items were fixed for the measured path only (first frame, `/assets/`, Chrome-with-`deviceMemory`). None of this has been measured on a physical cheap phone or on iOS WebKit, and the emulation tool cannot see GPU fill-rate, WebKit canvas limits or audio-session behaviour; F1, F2, F3 and F6 should be fixed in code before such a device test is worth running.
