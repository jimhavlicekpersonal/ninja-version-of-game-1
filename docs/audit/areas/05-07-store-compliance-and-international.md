## Findings

### A. Store policy (Apple / Google)

**C01 — High — VERIFIED — Play Age Signals plugin skips the mandatory access step, so it never obtains a signal in most regions.**
`android/app/src/main/java/com/toadstoolkingdoms/app/TkAgePlugin.java:40-45` calls `checkAgeSignals()` directly. Google's 0.0.4 flow (https://developer.android.com/google/play/age-signals/request-age-signals, read 2026-11-05) is two-step: `requestAgeSignalsAccess(AgeSignalsAccessRequest.builder().setActivity(...))` first, which shows Play's in-app consent prompt in user-choice regions and returns `SHARED | NOT_SHARED | VERIFICATION_REQUIRED`; only then `checkAgeSignals()`. Without the access call, user-choice regions never see the prompt (always "no_signal"), and in Texas-type states `VERIFICATION_REQUIRED` (user must verify in the Play Store app) is not distinguished from "unavailable", so the game silently falls back to its own self-declared screen where the law expects the store signal. `installId`, `significantChangeApprovalDate` are also unread. Also: API access must be requested in Play Console before it answers (owner). Suggested: add the `requestAgeSignalsAccess` step, surface `VERIFICATION_REQUIRED` as a distinct status that the HUD explains ("verify your age in the Play Store"), keep the band derivation.

**C02 — High — VERIFIED — iOS Declared Age Range: regulatory features, significant-update acknowledgement and consent revocation are not handled.**
`ios/App/App/TkAgePlugin.swift:33-58` handles only `.sharing`/`.declinedSharing`. Apple's age-assurance page (https://developer.apple.com/support/age-assurance/, read 2026-11-05): iOS 26.2 returns an age band or category by region and adds PermissionKit; 26.4 adds `AgeRangeService.requiredRegulatoryFeatures` and `showSignificantUpdateAcknowledgement(in:updateDescription:)`; 26.5 adds the `confirmed` value and apps "must rebuild against the 26.5 SDKs"; parental consent revocation arrives as App Store Server Notification `RESCIND_CONSENT`. `server/core/purchases.ts:318-320` handles only `REFUND`, `REVOKE`, `REFUND_REVERSED`. Suggested: build with Xcode 26.5 SDK, read `requiredRegulatoryFeatures`, define what a "significant update" is (legal decision), handle `RESCIND_CONSENT` server-side (suspend online play for that player), and test in Sandbox (Apple: age scenarios testable from 26.2).

**C03 — High — VERIFIED — Apple 1.2 "published contact information" and "timely responses" are not met in the shipped pages.**
`public/legal-config.js` has `supportEmail: ''`; `public/support.html:19` then renders "contact address not published yet". App Review Guideline 1.2 (read 2026-11-05) requires "Published contact information so users can easily reach you" and "timely responses to concerns"; `server/core/moderation.ts:113-118` falls back to "contact support from Settings → Privacy and help" when `supportContact` is unset, which points to the same empty page. `docs/legal/ONLINE_SAFETY_UK.md:88` confirms no response target exists. Suggested: fill `supportEmail`, set `ACCOUNT_SUPPORT_CONTACT` on the server, publish a response target once staffed.

**C04 — High — VERIFIED (code) / SUSPECTED (ruling) — Under-13 accounts exist with online play, push tokens, Alliance chat exposure and crash reports, but Play target audience is declared 13+ and no COPPA consent exists.**
`docs/store/PRIVACY.md` ("Families / Designed for Families: do not opt in… target audience 13–15, 16–17, 18+"); yet the code creates an `under13` band that keeps playing online (`privacy.html:39` "You can still play, raid and join an Alliance"), gets a push token (`server/core/pushTokens.ts` has no age check, grep = 0) and can turn on crash reports. Play's Families policy applies when a target audience includes children; selecting 13+ while the app knowingly serves under-13 players is a declaration-vs-behaviour mismatch Play can act on (https://support.google.com/googleplay/android-developer/answer/9893335; it also warns that "imagery and terminology… that could be considered targeting children" affects the assessment: cartoon ninjas, Sensei). Under COPPA (amended rule, compliance 2026-04-22) an under-13 band is actual knowledge. Also, an under-13 member of an Alliance still reads adults' free-text chat (only their own sending is restricted). Suggested (owner + code): decide one of (a) under-13 = offline only (simplest, consistent with 13+ declarations), (b) full COPPA/Families programme (parental consent, Families-approved SDKs: Sentry and Firebase Messaging would need review), or (c) internal-operations-only data for under-13 (no push, no crash reports, no Alliance chat display). Today's middle path is the weakest position.

**C05 — Medium — VERIFIED — Apple age-rating answers need two corrections.**
`docs/store/PRIVACY.md` answers "Contests: None". Apple's questionnaire (https://developer.apple.com/help/app-store-connect/reference/age-ratings-values-and-definitions/, read 2026-11-05): "Contests (competition for rankings, rewards, or goals): Infrequent 4+ / Frequent 13+". Honor leagues, Power Ranking, Alliance Wars and Gang Wars are frequent contests → answer Frequent (13+, no rating change but the answer must be true). "In-App Controls → Age assurance (declared age range API…)" is listed as a 4+ value; since the app does call the Declared Age Range API, answer Present, and it does not lower the 13+ rating. The Korea GRAC regional rating is derived from Apple's global rating (12+ → "12"), nothing else to file. Also note Apple's 2026-01-31 deadline for the new questionnaire has passed; new submissions must answer it.

**C06 — Medium — VERIFIED — Apple 5.1.1(v): the in-app deletion path and the "revoke social credentials" rule depend on a live server; nothing in Info.plist or the shipped pages links a deletion URL.**
`public/legal-config.js` `deletionUrl: ''`; `src/presentation/ui/hud.ts:1928` builds the link from `connection.url` only when a server URL is built in. OK once `VITE_SERVER_URL` and `deletionUrl` are set; flagged because Play's account-deletion policy requires the web link "must reference your app or developer name as it appears on your Play listing" (https://support.google.com/googleplay/android-developer/answer/13327111) and `server/accountPage.ts` says "Kagemura" but the Play listing name will be "Kagemura: Ninja Clans" (`LISTING.md`) — align the title.

**C07 — Medium — VERIFIED — iOS CI picks the newest installed Xcode on `macos-15`, which may not satisfy Apple's 2026-04-28 Xcode 26 rule or the 26.5 SDK for age assurance.**
`.github/workflows/ios-testflight.yml:12,43-52` (`runs-on: macos-15`, selects newest `/Applications/Xcode_*`, warns if SDK < 26). Apple: "Since April 28, 2026… Xcode 26 or later using an SDK for iOS 26" (https://developer.apple.com/news/upcoming-requirements/). GitHub's macos-15 image got Xcode 26.2 in Jan 2026 (runner-images release 20260112.0116); the 26.5/26.6 SDKs are on the `macos-26` image. Suggested: `runs-on: macos-26` and fail (not warn) below SDK 26.5.

**C08 — Medium — VERIFIED — StoreKit test configuration disagrees with the catalog.**
`ios/App/Products.storekit` lists game ids `moonstones_1..6`, `lantern_pass`, `offer_*` (11 products) while the app pays by store ids `jade_pouch`…`season_scroll` (`store.json` `storeProductIds`), and it lacks `jade_pinch` (`moonstones_0`, $0.99) and `clan_stipend` entirely. Local StoreKit testing (`docs/SHIPPING.md:78`) cannot work and the two newest products were never test-purchased. All are typed Consumable, which matches the catalog.

**C09 — Low — SUSPECTED — Clan Stipend as a consumable is defensible but should be described carefully in App Store Connect.**
`store.json` `stipend`: 30 daily Jade payments, days never lost, re-buyable only when empty, no auto-renew. Apple 3.1.2 governs auto-renewable subscriptions only; 3.1.1 "credits… may not expire" is satisfied because payments never lapse. Risk: a reviewer may read "daily payments" as a subscription if the ASC description says "monthly". Suggested: name it "30 Jade payments" in the product description, never "monthly"; keep the confirm text (`economyUi.ts:148`). Play: fine as an in-app product.

**C10 — Low — VERIFIED — Google Play age-rating for in-app products (Texas) is not prepared.**
Google's SB 2420 page (https://support.google.com/googleplay/android-developer/answer/16569691): "For Texas, you may need to assign age ratings to your SKUs". No SKU rating list exists in `docs/store/`. Owner step with counsel.

**C11 — Low — VERIFIED — Age-signal data handling has no written limit.**
Play's Age Signals policy (https://support.google.com/googleplay/android-developer/answer/16585319): use only for compliance/age-appropriate experiences; no selling/sharing/analytics. The server emits a Prometheus metric by band (`server/core/age.ts:44` `tk_age_bands_total{band}`) — aggregate counts are borderline "analytics" of age-signal-derived data. Suggested: keep metrics but document that bands derived from store signals are used only for protections; do not export per-band dashboards to third parties.

**C12 — Medium — VERIFIED — iOS `UIRequiredDeviceCapabilities = armv7` and deployment target 15.0 are fine, but Info.plist has no `CFBundleLocalizations`, `NSUserTrackingUsageDescription` is correctly absent, and `UISupportedInterfaceOrientations` allows landscape on iPhone with no `UIRequiresFullScreen`.** Only the localization point is actionable (see L-section). No change needed for tracking.

### B. Legal pages, operator identity, consumer law

**C13 — Critical (blocks EU/UK/JP/DE store listing) — VERIFIED — Every publisher fact is empty; pages render "not published yet".**
`public/legal-config.js`: `operator`, `operatorAddress`, `operatorPhone`, `responsiblePerson`, `supportEmail`, `deletionUrl`, `euRepresentative`, `ukRepresentative`, `hosting`, `crashReportRegion`, `governingLaw`, four retention fields, `termsEffective` all `''`; `tests/presentation/store-compliance.test.ts:74` asserts they are empty. Consequences: GDPR Art. 13(1)(a) controller identity missing; Germany's Impressum duty (DDG §5) unmet (no "Impressum" anywhere in `public/*.html`, grep = 0); Japan 特商法 notice incomplete; EU DSA trader address must match `operatorAddress`. Owner task before any store listing; see "Human/owner tasks".

**C14 — High — VERIFIED — Terms of service are a draft with no acceptance flow; Play UGC policy requires acceptance before UGC.**
`public/terms.html` shows a draft banner until `termsEffective` is set; `src/presentation/ui/communityRules.ts` records acceptance of the *community rules* (short version) only, stored in localStorage (`tk.community.accepted`), never on the server. Google Play UGC policy (https://support.google.com/googleplay/android-developer/answer/9876937): "Require users accept the app's terms of use and/or user policy before users can create or upload UGC." The rules acceptance arguably satisfies "user policy" but is per-device, not per-account, and is lost on reinstall (then re-asked, which is fine) but cannot be evidenced. Suggested: store `rules_accepted_version` on the player row and gate chat/name server-side.

**C15 — Medium — VERIFIED — Privacy policy lacks a few GDPR Art. 13 and CCPA items.**
`public/privacy.html` has purposes, bases, retention, rights, transfers, DPA complaint routes. Missing: (a) DPO contact (none appointed — Art. 37 likely not mandatory, but Brazil LGPD *encarregado* is: Art. 41); (b) automated decision-making note — the server auto-hides a message after 3 reports and the honor/rating system is automated but not "legal effects", so a one-line statement suffices; (c) CCPA "notice at collection" wording and the categories table with "sources" and "business purpose" per category; (d) the Art. 28 processor *list* names Sentry and hosting but with empty regions (`hosting`, `crashReportRegion`). (e) no last-reviewed statement for children's data (UK Children's Code DPIA not done, `docs/legal/MARKETS.md`). SUSPECTED for (c): threshold-dependent.

**C16 — Medium — VERIFIED — EU CPC virtual-currency principles: Jade-priced items show no real-money equivalent.**
CPC Key Principles (2025-03-21; the Commission opened coordinated action against nine game companies on 2025-09-30 per `docs/legal/MARKETS.md` sources): "real-world monetary values must be clearly displayed for both virtual currencies and the items they can purchase". Code: `economyUi.ts:183-190` `spendMoonstones` shows "for N Jade" only; top-up and skip quotes are Jade-only; packs have unequal Jade/USD ratios (45/0.99 … 7500/99.99) so "the" price is ambiguous. Soft law, but the enforcement wave targets exactly this. Suggested: show "≈ store price of the smallest pack that covers it" or a per-Jade reference price (owner/legal decision), EU-only if preferred; add parental-control hint for minors (already partly: no pop-up offers under 18).

**C17 — Medium — SUSPECTED (law) / VERIFIED (code) — Japan 資金決済法: the paid-balance report does not exist and the paid/free split is not stored.**
`docs/legal/JAPAN.md` §3 is a spec; `server/migrations/0023_purchase_storefront.sql` and `server/payments/apple.ts:41-44,149-150` capture Apple storefront/currency/price, but Google price capture and the base-date report (31 Mar / 30 Sep, ¥10M threshold, deposit of ≥½) are not built, and the game shows one Jade total. Also the Japanese pages are the only non-English pages (`tokushoho.html` `lang="ja"`), while `shikin-kessai.html` and the confirm step's Japanese links are triggered by *device language* (`economyUi.ts:29-36`), not by the App Store storefront — a Japanese-language device in the US gets them and an English-language device in Japan does not. Suggested: key on `PaymentProvider.prices` currency `JPY` (StoreKit storefront) rather than `navigator.language`; build the report before selling Jade in Japan; note Apple collects Japanese consumption tax on behalf of non-resident developers since 2025-04-01 (platform taxation, Apple Japan payment-options page).

**C18 — Medium — VERIFIED — Korea: no probability-item disclosure is needed (nothing random is sold), but a GRAC rating and, above thresholds, a domestic agent are owner steps; the game's free daily chest with shown odds is consistent.** Sources: `docs/legal/MARKETS.md` (Korea Herald, Shinkim); search 2026-11-05 confirms domestic-agent duty in force since 2025-10-23 and that disclosure duties apply independently. No code change.

**C19 — Medium — SUSPECTED — Brazil ECA Digital (in force 2026-03-17, Decree 12.880/2026): self-declared age is expressly not accepted as age verification for features aimed at minors.**
Search 2026-11-05 (Mattos Filho, Demarest): "the ECA Digital expressly prohibits relying on a user's simple self-declaration as an age-verification mechanism"; Apple added Brazil to Declared Age Range regions in Feb 2026 (MacRumors 2026-02-24). Code: `ageScreen.ts` is self-declaration; the Apple/Play signals are only a fallback source. For Brazil, chat/friends for minors may require a store-level or stronger age check and parental tools; a legal representative in Brazil is required for foreign providers. Nothing random is sold, so Art. 20 (loot boxes) is satisfied. Owner/legal task; code could make the store signal mandatory (no self-declaration fallback) for Brazil storefronts.

**C20 — Low — VERIFIED — EU ODR link correctly absent; consumer withdrawal text present; governing law empty.** `terms.html:80` governing law "not published yet". Owner task.

**C21 — Medium — SUSPECTED — European Accessibility Act exposure is unassessed.**
EAA applies since 2025-06-28 to "e-commerce services"; several law-firm readings say in-app purchase flows can bring an app into scope (Taylor Wessing 2025-03-24; Freshfields). Repo: `WORLDWIDE_AUDIT.md` R10 lists accessibility limits; `hud.ts` has 28 `aria-` attributes, modals trap focus, canvas has `role="img"`; no accessibility statement page exists (grep "accessibility" in `public/` = 0). Suggested: owner/legal decides scope (micro-enterprise exemption under Art. 4(5) may apply); if in scope, publish an accessibility statement and make the Store/confirm flow WCAG 2.1 AA.

**C22 — Low — SUSPECTED — India IT Rules 2021 (intermediary duties) and DPDP Rules 2025.** A game hosting user chat is an "intermediary": privacy policy + terms + a grievance officer with name and contact and a 24h-acknowledge/15-day resolution commitment; DPDP (verifiable parental consent for under-18 by ~May 2027). Nothing in `docs/legal/MARKETS.md` covers the IT Rules grievance officer. Owner/legal.

### C. Moderation and UGC

**C23 — High — VERIFIED — The word filter is 30 English words.**
`src/gameplay/data/social.json:136` `profanity` = `['damn', 'hell', … 'cunt']` (30 entries, all English). The filter engine (`grove.ts:96-111`) supports every script, but the list does not. **C24 — Medium — VERIFIED — Community rules, notices and appeal texts are English only; `community.html` and `terms.html` are `lang="en"`.** `server/core/moderation.ts:113-118`, `PRESET_CHAT` in `src/backend/net/protocol.ts:1093` (8 English phrases: an under-13 Japanese or Arabic player can only send English). Suggested: localise `PRESET_CHAT` by key (send the key, render per language) once the text layer exists.

**C25 — Low — VERIFIED — Typed URLs are stripped in chat (`grove.ts:86-93`), but the rule set does not cover obfuscated handles ("d1sc0rd", "tele gram"), and names are not run through `stripContacts`.** `censorText` (names) does not call `stripContacts`; a name like "add me on tg 1234567" passes if under 24 width. Suggested: run `stripContacts` on names too (reject rather than replace).

### D. Localization and international text

**L01 — High — VERIFIED — The game ships in English only; the translation pipeline does not cover the UI at all.**
`node tools/i18n/i18n.mjs status`: 49 target languages, 0/648 done in every one; the 648 strings are *game data only* (`locales/en/data.json` generated from `src/gameplay/data`). UI text lives as literals: a rough count finds 516 multi-word quoted strings in `src/presentation/ui/*.ts` (plus server messages, notices, legal pages) that are in no worksheet. `index.html` is `lang="en"`; `CLAUDE.md` confirms "The game does not read `locales/` yet". `docs/prompts/DOWNLOAD_AND_LANGUAGE.md` is a prompt; its plan file `docs/backend/DOWNLOAD_AND_LANGUAGE_PLAN.md` does not exist. So: 0 of 50 languages playable; listing must stay English-only (`LISTING.md` already says so).

**L02 — Medium — VERIFIED — Plurals and concatenation that cannot be translated.** 22 `? 's' : ''` patterns in `src/presentation/ui/*.ts` (e.g. `armyUi.ts:384,475`, `economyUi.ts:334`, `dailyUi.ts:92`), server strings interpolate English (`moderation.ts:96`). Russian/Polish/Arabic need one/few/many; Turkish suffixes attach to numbers (`languages.json` note). Suggested: `Intl.PluralRules` + keyed messages when the text layer is built.

**L03 — Medium — VERIFIED — Number and date formatting is inconsistent.** `src/presentation/ui/format.ts:4` forces `toLocaleString('en-US')` (so 1,234 everywhere, including Germany/India/Arabic digit conventions), `pass.ts:245` same; dates use the device locale (`hud.ts:735,921,943,1499`). `languages.json` says Arabic should use Western digits "the game formats numbers" — true today only because everything is en-US.

**L04 — Medium — VERIFIED — Fonts cover Latin only; other scripts fall to system fonts, and RTL has no layout.** `src/presentation/ui/fonts/README.md`: both woff2 files are "Latin subset"; `styles.css:42` fallback stack lists Hiragino/Noto/Geeza/Nirmala/Thonburi etc. (good), but the display font Dela Gothic One will not render titles in CJK/Arabic/Devanagari/Thai/Ethiopic (Amharic has no fallback named; `system-ui` catches it). No `dir="rtl"` handling anywhere in CSS (grep = 0 beyond `dir="auto"` on names); `AndroidManifest` `supportsRtl="true"` is Capacitor's default and does nothing for the web layout. Canvas art has no text (`fillText` = 0 in `art/`, `render/`), which is good: no localized textures needed.

**L05 — Low — VERIFIED — Time-zone fairness: daily chest, streaks, stipend claims and the under-18 cap are UTC-day based.** `src/gameplay/sim/daily.ts:4,39` (`dayIndex` = UTC days since epoch), `store.json` stipend "per UTC day", `purchases.ts:99` `monthStart` UTC. A player in Auckland (UTC+13) gets the daily reset at 13:00 local; in Honolulu at 14:00 the previous day. Not unlawful, but the privacy page and listing should not say "daily" without "(UTC)"; `privacy.html` does not mention it. Quiet hours for push are correctly local (`reminders.ts:72-82`).

**L06 — Low — VERIFIED — Names policy is script-complete and server-enforced (UTS #39 mixing, width 24, pinned segmenter) — no finding; but the English `NAME_ERROR_TEXT` (`names.ts:30-34`) and server rejection reasons are untranslated.**

**L07 — Low — VERIFIED — Japanese legal pages are keyed on device language, not storefront (see C17).**

### E. International availability and infrastructure

**I01 — Medium — VERIFIED — Single-region server; region undecided; data-residency undeclared.** `docs/SHIPPING.md:92-95` (Render/Railway/Neon/Fly, one web service); `legal-config.js` `hosting: ''`, `crashReportRegion: ''`. Latency for Asia/Africa/LatAm against a single US/EU instance will be 150–350 ms per request; the audit's R04 polling (chat every 4 s) multiplies that. Suggested: pick the region from target markets (EU for GDPR simplicity, or US), put a CDN/anycast TLS terminator in front, set Sentry EU region if EU players, and state both in the policy. The PWA on GitHub Pages is globally CDN-served (Fastly) — fine.

**I02 — Medium — SUSPECTED — Install size vs data cost is good for web (~0.6 MB first visit, `DOWNLOAD_AND_LANGUAGE.md`), unverified for native (Capacitor + Billing + Credentials + Firebase + Age Signals AARs; typically 8–15 MB AAB download).** Measure the signed AAB/IPA before claiming "small".

**I03 — Low — VERIFIED — Every update re-downloads everything on the web** (`DOWNLOAD_AND_LANGUAGE.md` §1: cache name per build, Phaser bundled in the same hashed file) — a real cost on metered connections in target markets.

**I04 — Low — SUSPECTED — Sanctioned/paymentless markets.** Russia and Belarus: both stores list apps but card payments are suspended (Apple since March 2022; Google Play Russia billing paused) — purchases will fail; the server's `purchases` paths handle a store "not sold here" gracefully (`PaymentProvider.prices` → "Not sold here"). Cuba, Iran, North Korea, Syria, Crimea/DNR/LNR: exclude in both consoles (store defaults mostly do). Owner territory step.

**I05 — Low — VERIFIED — IPv6: the server listens on IPv6 and `check-domain.mjs` tests it (`docs/SHIPPING.md`, `tools/ops/check-domain.mjs`); carrier-grade NAT limits are loose (`rateLimit.ts` 3,000/min per /64). Good for Asian/African mobile carriers.**
