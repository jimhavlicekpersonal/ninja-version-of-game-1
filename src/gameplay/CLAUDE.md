## Architecture rules (unchanged from the original spec)

1. `sim/` is pure and deterministic: no Phaser, DOM, `Date.now()` or `Math.random()` (enforced by `tests/gameplay/sim/purity.test.ts`). It imports nothing outside `gameplay/` (boundary test).
2. Every balance number is in `data/*.json`. No magic numbers in code.
3. Time comes from the injected `Clock`. Timers store `startedAt`/`endsAt`.
4. Offline progress is computed on load from elapsed time.
5. Battles: fixed 10 ticks/s, seeded RNG, replayed exactly from `seed + deployments`. Only use + − × ÷ and √. Abilities (Smoke Bomb) are deployments whose `troop` is an ability id. The server re-simulates every attack with this same code.

## Key systems

- `sim/battle/battle.ts`: combat, Smoke Bomb (warriors inside the cloud are shot from range × 0.4, never below 2 tiles, 8 s, no stacking, charges from army housing), Sabotage (6 s jam, then 10 s immunity after recovery, one jam per Saboteur). `SIM_RULES` versions the battle rules: bump it (and the fingerprint in `tests/gameplay/battle/rules-version.test.ts`) whenever combat data or rules change; records carry it and only matching replays are shown. Wall-breakers (`prefers: 'walls'`) break the wall between them and the nearest defense or Keep (`wallInTheWay`). `BattleSetup.reinforcements` deploys donated troops first at their donated level. `activeInBattle(b)`: an upgrading building neither fires nor runs its counter effect.
- Relay strikes (SIM_RULES 3): `BattleSetup.startDamage` (HP lost per building; a building at its HP starts destroyed) and `battleDamage(sim)`. `SIM_RULES_COMPATIBLE` lists older rules this code plays exactly; empty it on the next real change to combat. Gang Wars: `sim/social/gangWar.ts` (phases, outcome, deterministic bot Gang, `carryRelayDamage`), `social.json` `gangWar`, `claimGangChest` (save v13), `rateTeams` in `sim/rating.ts`.
- `sim/battle/fortifications.ts`: the five live defensive counters (`BuildingEffect` in `buildings.json`, per-level overrides in `levels[].effect`). Lantern light and ballista grounding live on `SimTroop` (`litUntil`, `groundedUntil`); incense cuts are recomputed every tick. Use `airborne(sim, t)`, not `t.air`, for targeting layers.
- `sim/battle/infiltration.ts`: Infiltration Points. `planInfiltration` builds the points from the layout (deterministic), `canDeploy` enforces point + cover, `deployBlock` says why a tap failed. Set `infiltration: true` on every new `BattleSetup` (app, Alliance raids, bot raids, server); leave it off only for old records. `botDeployments(..., entry)` deals each troop type round the nearest `minPoints` points.
- Sim events `ability` / `counter` exist only for on-screen feedback; they never affect the result hash.
- `sim/battle/basegen.ts`: generated bases, five layout archetypes; support counters with an effect radius are placed where they cover the most defenses. `scout.ts`: what scouting reveals (never hidden traps, never upgrading buildings as threats).
- `sim/trials.ts` + `data/trials.json`: Shadow Trials, the endless ladder, rewarded once per tier through the `trialEnd` command. Each tier is the median-strength of `candidates` generated fortresses, with a `layoutPower` factor per layout; after a failed attempt the player may switch the next tier to an alternate fortress (`trialAlternate`, same reward).
- Settlement: `advance` finishes timers in the order they ended and rolls task days/weeks and league seasons at their real boundary (`settleSeasons`, `seasonLog`). Rewards report what was really added (`grantReward` → granted + overflow; `rewardOverflow`, `dailyChestOverflowRisk` warn first). Attack records keep `result.loot` (the battle's own), `banked` and `overflow`. Online attacks (`battleEnd` with `ticket`) are `settlement: 'pending'` until `settleOnlineAttack`. Online raid losses come out of the building that lost them (`applyDefenseLosses`).
- Army: Dojo `trainingSpeed`, a next-army queue (a finished warrior too big for the space left waits, and anyone behind who fits walks past: `finishTraining`, and `queueFits` for quotes and the panel), `train` with a count, `fillCount` (what Fill queues: the camps first, the next army only after that), `trainArmy` (refill to a preset or the last army; `train_short` reports what didn't fit), `saveArmyPreset`/`deleteArmyPreset`, `dismiss` (50% back), `practiceArmy` for no-stakes practice battles. `skipTraining` finishes the warriors who fit (`queueFits`); the rest keep training. `cancelTraining` works back from `index` through one type and takes `troop` because the queue can move under a stale index; `retimeQueue` never touches a finished warrior or the one in training. A queue timer must never end before it began: `validateVillage` rejects that, and a failed load replaces the village (`repairTrainingQueue` guards this on load). Research runs in `researchLanes` lanes (one per troop type); `cancelResearch`/`skipResearch` take a troop.
- `sim/armyView.ts`: everything the Army panel shows, from one settled copy of the village (`armyView`, then `trainRow`/`researchRow` per warrior). Inside a loop use `trainQuoteOn`/`researchStartQuoteOn` on a settled village: `trainQuote` copies the whole village each call.
- Top-ups: `topUp` carries the action it pays for (`TopUpAction`: upgrade, place, train, research). `topUpQuote`/`topUpQuoteOn` price only the shortfall at the buyer's Keep (`topUpScale`), and only when resources are the one thing stopping the action. The action runs in the same command, so a failure buys nothing. There is no free-standing exchange (`docs/game-theory/TOP_UP.md`). `trainingSkipQuote` uses `trainingSkipCost` (time price × `trainingSkipScaleByHall`), because skipping training and raiding is the other route from Jade to resources.
- Matchmaking: `opponentFor` uses honor but never below `attackerStrength` (Keep + research progress, with each troop's level read as level + `levelCapOffset`, so fresh new-tier warriors don't lower it) minus `powerSlack`.
- Tasks: `rollPeriods` fixes the day's and week's task ids from `taskEligible` ones when the period begins.
- `sim/progression.ts` + `data/progression.json` + `data/roster.json`: the power-budget model. All 50 warriors are playable through Keep 15. Four heroes and the non-live buildings remain planned (20 of them carry `counters`/`counteredBy` against the roster; `building-matchups.test.ts`).
- `sim/battle/warriors.ts`: data-driven warrior abilities (`TroopDef.kit` in `troops.json`). Auras, same-type poison and overlapping same-type burning do not stack. Jams/stuns share recovery immunity. Companions split their owner's stat budget and never consume extra inventory. Per-battle effects reconstruct from seed + deployments.
- Training checks both `unlockKeep` and Dojo level; research uses each troop's `levelCapOffset`. Keep-indexed economic tables cover 1–15. Preserve all original six-unit stats through level 5, except Kite Raider (`owl_bomber`), which took the air-role cut (0.45× HP, 0.75× damage) with the other flyers.
- `control/controller.ts`: command dispatch, saving. `onCommand` tells listeners about every successful command and its time; `adoptEconomy` puts a server's economy in place and replays queued commands; `adoptVillage` swaps in a server village (the old one becomes a backup). `control/battleSession.ts`: real-time battle stepping.
- Purchases (roadmap Phase 4): `grantPurchase` takes `verified` (the server checked the receipt: delivered even if the offer ended or the age check would now refuse; a repeated transaction id is still refused) and is no longer a player command; `revokePurchase` and `staffAdjust` (server only: a refund, a staff correction; never below zero) take a refund back as far as it is still there and the Season Scroll if it was this season's. `monetization.ts`: `storeProductId`/`productForStoreId` (`store.json` `storeProductIds`), `monthStart`. `reminders.ts`: `inQuietHours`, `localDay` (shared with server push); `notifications.json` has the push types `raided` and `donations`.
- `sim/rating.ts` + `ranks.json` `rating` (roadmap Phase 3, shared with the server): hidden Attack/Base Ratings, `expectedScore` with the power term, `rateBattle`, `orderByRating`/`pickByRating` (matchmaking), `powerRating`, `layoutChangedShare`. The server uses these exact functions; `tests/gameplay/balance/rating-convergence.test.ts` simulates weeks of model players through them. Changing the `rating` numbers changes live matchmaking: rerun it.
- `sim/serverEconomy.ts` (shared with the server, roadmap Phase 2): `Economy` (resources, buildings, next id, army, training, research, Lodge) is what a server-held village checks; `economyHash` (FNV-1a 64 of `canonicalJson`) must be identical in browser and Node; `withEconomy` swaps it in; `PLAYER_COMMANDS` lists the commands a player may send (everything else is a server result or device-only); `BATTLE_COMMANDS` re-run a battle on the server. Changing the economy's fields, `PLAYER_COMMANDS`, or a command's effect changes what the server replays: tell BACKEND, and keep `applyCommand` pure. `battleEnd` / `remoteGroveBattleEnd` take an optional `known` result and `applyDefense` an optional `fallen` list: server-only shortcuts so a battle is simulated once per request; the game never sets them.
