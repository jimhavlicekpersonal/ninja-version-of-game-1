## Multiplayer (ports and adapters)

- `net/protocol.ts`: routes, types, error codes and `PROTOCOL_VERSION` (now **6**, `minProtocol: 6`: the gameplay audit changed the battle rules (`SIM_RULES` 2), added `BattleSubmission.reinforcements` (donated troops and their levels) and `DefenseView.reinforcements`/`rules`). `checkArmy` checks own troops against `troopEarliestKeep` and full camps, donated troops against the Lodge, and research caps; `normalizeBase`/`validateBase` enforce the Keep's counts and levels, an allowlisted shape (no `power`/`wallPower`), and `capBaseLoot` drops loot from buildings that can't hold it. A used ticket stores its answer (`Ticket.response`, `tickets.response` column): a repeated report gets the same answer back, never a second settlement. Each ticket carries a server-issued battle seed (`Ticket.seed`, `MatchResponse.seed`, `RaidTicketResponse.seed`); the server re-simulates with it and `battleSeed` refuses a report played with another (the client never picks online seeds). Wars pair equal rosters (strongest members, smaller side's size), cap each side's attacks at roster × allowance, and break star ties by destruction. Bump the protocol for incompatible simulation changes and update `docs/PROTOCOL.md` and contract tests.
- `net/connection.ts`: online attacks are settled from the server's answer (`settleOnlineAttack`); a permanently refused report becomes a practice result; pending attacks missing from the outbox are re-queued from the battle log. `ensureFreshBase` uploads the base before matching when the Keep changed (the server validates against it). `offline: true` keeps the testing sandbox off the network.
- Saves: `persist/saveStore.ts` stores a revision with each save and checks it in the same transaction as the write, so a stale tab gets `SaveConflictError` instead of overwriting newer progress. `backupDamaged` copies are listed by `listBackups` for recovery. The revision lives on the stored file, not in the village, and is not a format change.
- Payments: `payments/select.ts` decides the path: the instant mock store only in the testing sandbox (`?sandbox`/`?debug`, separate save), StoreKit on iPhone, otherwise unavailable.
- `net/ports.ts` → `ServerPort`; adapters `httpAdapter.ts` and `server/inProcess.ts`. `net/connection.ts` brings server results in only through idempotent commands, deduplicated by `state.net`. Battle reports go through a persisted outbox.
- `social/groveSource.ts`: `LocalGroveSource` (bot Alliance) and `RemoteGroveSource` (server).
- `server/core/` holds every server rule, with no HTTP or DB code. It reaches the outside only through `ServerContext` and the `Repo` port (`MemoryRepo`, `PgRepo`). `server/app.ts` is a thin Fastify adapter.
- Each distinct base is stored once (`base_versions`, key `contentHash` = SHA-256 of canonical JSON); tickets and attack records refer to it, written in the same statement. Both repo adapters do this, so the core still passes whole bases around. `server/core/retention.ts` keeps replays and tickets 30 days (unused tickets a day after expiry) and removes unreferenced bases; `server/main.ts` runs it hourly.
- Shared state (`server/shared.ts`, step 16): `ctx.board` (`Leaderboard`) and `ctx.locks` (`MatchLocks`) default to the database (`RepoLeaderboard`, `TicketLocks`); with `REDIS_URL` they are a Redis sorted set and SET NX locks (`server/redis.ts`, a small RESP client, no dependency), and rate limits use `RedisRateLimiter`. Postgres stays the truth: update `ctx.board` wherever honor changes or a player gets a base or is deleted. `TEST_REDIS_URL` runs the Redis tests.
- Observability (step 17): `server/observability.ts` (`Metrics` port → `ctx.metrics`, `PromMetrics` at `/metrics` behind `METRICS_TOKEN`, `ServerSentry`), `ctx.log` for structured lines, `x-request-id` on every answer, `/healthz` (liveness) and `/readyz` (dependencies). `resimulate` in `core/pvp.ts` times every re-simulation and counts desyncs against `BattleSubmission.clientHash`. Game crashes: `analytics/crashReports.ts` (`VITE_SENTRY_DSN`, the `crashReports` pref); both sides build envelopes with `analytics/sentryEnvelope.ts` (no SDK, no player data). Add a `METRIC_HELP` line for every new metric.
- Limits live in the HTTP adapter: `server/rateLimit.ts` (`RateLimiter` port, memory counters per instance until Redis in step 16; rules per IP, per token hash, and per route through `config.rate`) and `BODY_LIMITS` per route. `429 rate_limited` is retryable for the client (`ServerError.retryable`), so the outbox keeps a rate-limited report. Set `TRUST_PROXY` behind a load balancer.
- Account deletion: `DELETE /v1/me` → `server/core/account.ts` → `Repo.deletePlayer` (one transaction: deletes what is only the player's, keeps what others hold as `DELETED_PLAYER`). Any new table that stores player data must be handled there too. Web requests (`/account/delete` page, `POST /v1/account/deletion-requests`) wait for staff in the admin API (`ADMIN_TOKEN`, `/admin/v1/…`, `server/app.ts`). `Connection.deleteAccount` switches online play off on the device so it does not silently re-register.
- Reports and blocks: `server/core/moderation.ts` (Apple 1.2). Chat reports keep the message text; 3 distinct reporters hide a message (`grove_chat.hidden`) until staff act; blocks filter chat and troop requests per viewer; mutes (`players.muted_until`) refuse chat with `403 muted`. Staff: `/admin/v1/reports`. Any new surface with player-written content (Friends, Gangs, duels) needs report and block too (roadmap 5.9). `RemoteGroveSource` offers them only when `/v1/hello` lists `reports`; the bot Alliance never does.
- Database changes are numbered files in `server/migrations/` (`0002_what_it_does.sql`), applied by `npm run server:migrate` as a release step (`server/migrate.ts`: checksums, an advisory lock, one transaction per file). The server refuses to start with pending migrations unless `MIGRATE_ON_BOOT=1`. Never edit an applied file; add a new one, and keep each change backward compatible with the previous server build (rolling deploys).
- The server re-simulates every attack with `runBattle`. Smoke charges come from the army (`smokeCharges`), so no new stored fields are needed. The server applies the loot penalty once. The client must not apply it again.
- **Honesty rule:** when nobody fits, the server sends a generated base with `opponent.kind: 'bot'`; the client labels it. Simulated raids are flagged `simulated: true`.
- Internal names stay stable (`grove`, `toadstool-kingdoms` in `/v1/hello`). See `docs/rebuild/ID_MAP.md`.

## Monetization and compliance (keep these rules)

- Payments go through `PaymentProvider`: mock (testing sandbox only), StoreKit 2 (iOS, `ios/App/App/TkStorePlugin.swift`). **Android and public web purchases are disabled** until a real web/Play payment path is added; ask the owner first.
- Real prices only in the Store and its confirm step. Clear confirm on every purchase (FTC/Epic lesson). Under-18 spending cap. Chat filter on.
- Paid random items need their odds shown before purchase (App Review 3.1.1), and the loot-box laws in each market must be checked first. The daily chest is free and never sold. Streak repairs, ability charges and trial rewards are never sold.
- New app identity: the display name is "Kagemura". The bundle id is still `com.toadstoolkingdoms.app`, and product ids are unchanged. Changing them means a new App Store / Play listing (owner steps in `docs/SHIPPING.md`).
