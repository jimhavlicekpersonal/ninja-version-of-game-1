# BACKEND compartment (Section 3): multiplayer, monetization, store compliance

You are the **BACKEND AI**. You own `src/backend/` (net, social, payments, platform, persist, analytics, pwa), `server/`, `docs/PROTOCOL.md`, `docs/SHIPPING.md`, `ios/`, `android/` and `.github/workflows/`. You call game rules from `src/gameplay/sim`, and never fork or change them.

**Roadmap:** `docs/backend/PVP_ROADMAP.md` is the agreed design and step list for the PvP server (ratings, hosting and cost, protocol 7 payloads, store payments, Friends, Friendly Duels and Gang Wars). Mark steps done there as you finish them.

## Multiplayer (ports and adapters)

- Game versions (Phase 1.5, protocol **8**, servers accept 7): `net/dataVersion.ts` (data version, combat fingerprint, build compare), `server/rules/registry.ts` (`ctx.rules`: the live engine plus archived snapshots in `server/rules/v<N>/`, made by `npm run rules:snapshot` before a `SIM_RULES` bump and never edited; `RETIRED_RULES`, `MIN_CLIENT_BUILD`). Every ticket stores `rules`/`dataVersion`; `engineForClient` / `engineForTicket` in `core/pvp.ts` pick the engine; re-simulation, army checks and bot bases use it. `net/versionCheck.ts` + `Connection` status `incompatible` + HUD "Update Kagemura". Release guard `tools/release/check-server-rules.mjs`; dashboard `ops/grafana/game-versions.json`. Balance bundles (step 76): `net/balanceBundle.ts` (checks), `net/balance.ts` (`BalanceLoader`, applied at start only), `BALANCE_BUNDLE_FILE`/`BALANCE_PUBLIC_KEY`, `npm run balance:bundle`.
- Duels, Gangs, Gang Wars (steps 62-70): `server/core/duels.ts`, `squads.ts` (roster lock from `gangWars.ts` via `setRosterLock`), `gangWars.ts` (queue, prep, solo/relay tickets, relay hold in `squad_war_relays`, `carryRelayDamage`, claims, `rateTeams`, `gangWarReminders`), migrations 0016-0017. Gang chat and requests reuse `groves.ts` `chatIn`/`requestTroopsIn`/`donateIn` with the Gang id. Game side: `Connection` duel/Gang/war methods, `gangWarBattle` (outbox kind `gangwar`, `PendingBattle.channel`), `claimGangChests` on sync.
- Names and friends (steps 59-61): `net/names.ts` (rules, shared), `server/core/names.ts` (claim, strict rename with suggestions, holds, `migrateNames` at start), `server/core/friends.ts` (lookup, codes, requests, privacy, platform friends), migration 0015, `Connection` friends methods. `Repo.updatePlayer`/`createPlayer` throw `NameTakenError` on a name-key or friend-code clash. Any new player-facing surface (duels, Gangs) needs Report and Block, and account deletion must clear its rows.
- `net/protocol.ts`: routes, types, error codes and `PROTOCOL_VERSION` (now **8**; before that 7, `minProtocol: 7`, roadmap step 26: `ClientHeaders` on every request, idempotent writes through `Idempotency-Key` (`idempotency_keys`, a day), `426 version_mismatch` for older games; features from steps 10–32 are listed in `/v1/hello`; before that, 6: the gameplay audit changed the battle rules (`SIM_RULES` 2), added `BattleSubmission.reinforcements` (donated troops and their levels) and `DefenseView.reinforcements`/`rules`). `checkArmy` checks own troops against `troopEarliestKeep` and full camps, donated troops against the Lodge, and research caps; `normalizeBase`/`validateBase` enforce the Keep's counts and levels, an allowlisted shape (no `power`/`wallPower`), and `capBaseLoot` drops loot from buildings that can't hold it. A used ticket stores its answer (`Ticket.response`, `tickets.response` column): a repeated report gets the same answer back, never a second settlement. Each ticket carries a server-issued battle seed (`Ticket.seed`, `MatchResponse.seed`, `RaidTicketResponse.seed`); the server re-simulates with it and `battleSeed` refuses a report played with another (the client never picks online seeds). Wars pair equal rosters (strongest members, smaller side's size), cap each side's attacks at roster × allowance, and break star ties by destruction. Bump the protocol for incompatible simulation changes and update `docs/PROTOCOL.md` and contract tests.
- `net/connection.ts`: online attacks are settled from the server's answer (`settleOnlineAttack`); a permanently refused report becomes a practice result; pending attacks missing from the outbox are re-queued from the battle log. `ensureFreshBase` uploads the base before matching when the Keep changed (the server validates against it). `offline: true` keeps the testing sandbox off the network.
- Saves: `persist/saveStore.ts` stores a revision with each save and checks it in the same transaction as the write, so a stale tab gets `SaveConflictError` instead of overwriting newer progress. `backupDamaged` copies are listed by `listBackups` for recovery. The revision lives on the stored file, not in the village, and is not a format change.
- Payments: `payments/select.ts` decides the path: the instant mock store only in the testing sandbox (`?sandbox`/`?debug`, separate save), StoreKit on iPhone, Play Billing on Android only when built with `VITE_PLAY_BILLING=1`, otherwise unavailable. With a server that checks the store (`/v1/hello` `purchases-apple|google`), `GameController.purchase` asks `PurchaseVerifier.intent` first (age cap; `403 purchase_refused` before paying), pays the store id with the intent's token, redeems the receipt, delivers what the server confirmed (`grantPurchase` with `verified`), and only then finishes the store transaction (`PaymentProvider.finish`); `deliverUnfinished` (start, connection) and `deliverReceipt` (Ask to Buy) cover the rest. `Connection.purchaseVerifier(store)` is null for a device village on a server that does not check that store (trusted, as before Phase 4), and refuses for a server-held village there.
- Purchases on the server (Phase 4): `server/payments/apple.ts` (JWS: x5c chain to Apple Root CA - G3 pinned by fingerprint, marker OIDs, ES256), `google.ts` (service-account OAuth, Play Developer API, consume, RTDN via OIDC, Voided Purchases), `server/core/purchases.ts` (intent, redeem once per store transaction in a transaction with the village grant, history, `revoke`), migrations 0010 (`purchases`, `purchase_intents`). Purchase records are kept on account deletion, unlinked (`DELETED_PLAYER`). Test receipts: `tests/backend/fixtures/appstore/` (a made-up chain, never Apple's).
- Push (step 40): `server/push/push.ts` (`Pusher` → `ctx.push.notify`, fire and forget; `ServerPush` applies per-device types, quiet hours and `maxPerDay` with `inQuietHours`/`localDay` from `sim/reminders.ts`; `ApnsTransport` HTTP/2 + ES256, `FcmTransport` v1), migration 0011 (`push_tokens`), `PUT|DELETE /v1/push/tokens`; game side `platform/push.ts` + `Connection.syncPush`/`pushTypes`. Pushes today: `raided` (attack), `donations` (donate), `groveRaid` (pairing made).
- Operations (steps 44–48): `tools/ops/` (backup, restore, restore-check, check-domain), `.github/workflows/backup.yml`, `server/load.ts` + `loadMain.ts` (`npm run server:load`), gauges on `PromMetrics.gauge` (`tk_db_pool_connections`, `tk_event_loop_delay_ms`) and `ops/prometheus/alerts.yml` (a test checks its metric names), `SERVER_NOTICE` → `/v1/hello` `notice`. Admin tool: `server/core/admin.ts` + `server/adminPage.ts` (`/admin`, `/admin/v1/players…`, `/admin/v1/actions`), migration 0013 (`players.banned_until`, `staff_actions`); a banned player gets `403 banned` (`Connection` status `suspended`) and every ranking query skips `banned_until <> 0`. Every staff action must go through `audit()`.
- Deployments (step 42-43): `server/config.ts` (`DEPLOY_ENV`, `checkConfig`, `paymentsFromEnv`), migration 0012 (`server_meta`, `PgRepo.claimEnvironment`), `Dockerfile`, `.github/workflows/server.yml`, `tools/release/` (deploy hook, previous-release contract tests).
- `net/ports.ts` → `ServerPort`; adapters `httpAdapter.ts` and `server/inProcess.ts`. `net/connection.ts` brings server results in only through idempotent commands, deduplicated by `state.net`. Battle reports go through a persisted outbox.
- `social/groveSource.ts`: `LocalGroveSource` (bot Alliance) and `RemoteGroveSource` (server).
- `server/core/` holds every server rule, with no HTTP or DB code. It reaches the outside only through `ServerContext` and the `Repo` port (`MemoryRepo`, `PgRepo`). `server/app.ts` is a thin Fastify adapter.
- Each distinct base is stored once (`base_versions`, key `contentHash` = SHA-256 of canonical JSON); tickets and attack records refer to it, written in the same statement. Both repo adapters do this, so the core still passes whole bases around. `server/core/retention.ts` keeps replays and tickets 30 days (unused tickets a day after expiry) and removes unreferenced bases; `server/main.ts` runs it hourly.
- Shared state (`server/shared.ts`, step 16): `ctx.board` (`Leaderboard`) and `ctx.locks` (`MatchLocks`) default to the database (`RepoLeaderboard`, `TicketLocks`); with `REDIS_URL` they are a Redis sorted set and SET NX locks (`server/redis.ts`, a small RESP client, no dependency), and rate limits use `RedisRateLimiter`. Postgres stays the truth: update `ctx.board` wherever honor changes or a player gets a base or is deleted. `TEST_REDIS_URL` runs the Redis tests.
- Observability (step 17): `server/observability.ts` (`Metrics` port → `ctx.metrics`, `PromMetrics` at `/metrics` behind `METRICS_TOKEN`, `ServerSentry`), `ctx.log` for structured lines, `x-request-id` on every answer, `/healthz` (liveness) and `/readyz` (dependencies). `resimulate` in `core/pvp.ts` times every re-simulation and counts desyncs against `BattleSubmission.clientHash`. Game crashes: `analytics/crashReports.ts` (`VITE_SENTRY_DSN`, the `crashReports` pref); both sides build envelopes with `analytics/sentryEnvelope.ts` (no SDK, no player data). Add a `METRIC_HELP` line for every new metric.
- Limits live in the HTTP adapter: `server/rateLimit.ts` (`RateLimiter` port, memory counters per instance until Redis in step 16; rules per IP, per token hash, and per route through `config.rate`) and `BODY_LIMITS` per route. `429 rate_limited` is retryable for the client (`ServerError.retryable`), so the outbox keeps a rate-limited report. Set `TRUST_PROXY` behind a load balancer.
- Account deletion: `DELETE /v1/me` → `server/core/account.ts` → `Repo.deletePlayer` (one transaction: deletes what is only the player's, keeps what others hold as `DELETED_PLAYER`). Any new table that stores player data must be handled there too. Web requests (`/account/delete` page, `POST /v1/account/deletion-requests`) wait for staff in the admin API (`ADMIN_TOKEN`, `/admin/v1/…`, `server/app.ts`). `Connection.deleteAccount` switches online play off on the device so it does not silently re-register.
- Reports and blocks: `server/core/moderation.ts` (Apple 1.2). Chat reports keep the message text; 3 distinct reporters hide a message (`grove_chat.hidden`) until staff act; blocks filter chat and troop requests per viewer; mutes (`players.muted_until`) refuse chat with `403 muted`. Staff: `/admin/v1/reports`. Any new surface with player-written content (Friends, Gangs, duels) needs report and block too (roadmap 5.9). `RemoteGroveSource` offers them only when `/v1/hello` lists `reports`; the bot Alliance never does.
- `Repo.transaction(fn)`: everything written through the `tx` handle lands together (Postgres: one connection, nested calls are savepoints; memory: queued, every field restored on error). Use it whenever one request changes more than one row that must agree (attacks with server-held villages, command batches).
- Linked sign-ins (step 24): `server/identity/verify.ts` checks Apple/Google ID tokens (JWKS), Game Center signatures (key URL on `*.apple.com` only) and Play Games codes with node:crypto; `identity_links` keeps only the provider's stable id; `player_tokens` gives each device its own token (`POST /v1/sessions`). The game asks the platform through `platform/auth.ts` (a contract file; iPhone `TkAuthPlugin.swift`; web Google Identity Services / Sign in with Apple JS); a new device adopts the server-held village. Android sign-in is not done (needs the Play services SDKs).
- Moving a village (step 25): `server/core/villageImport.ts` (`importProblem`: what no village at its Keep could hold), stored exactly as sent. `Connection.keepVillageOnServer` (set by `main.ts`) moves it when the server can take it; a refusal is kept (`villageMoveRefused`) and shown.
- Ranking (steps 28–31): `attack()` rates both sides with `sim/rating.ts` inside its transaction (never against bots), applies the daily honor-loss cap, and `match()` orders candidates with `orderByRating`; `layoutReset` restarts a Base Rating after a big layout change; `GET /v1/leaderboard/power`.
- The game's side (step 21): `net/villageSync.ts` (`Connection.village`) hears `GameController.onCommand`, queues `PLAYER_COMMANDS` with time and hash in local storage, flushes before attack reports, and applies corrections with `adoptEconomy` (replaying what is still queued). Never send a server result (`settleOnlineAttack`, `applyDefense`, …) as a command.
- Server-owned villages (Phase 2, steps 19–22, feature `server-economy`): `server/core/village.ts` replays the game's own commands (`PLAYER_COMMANDS` in `src/gameplay/sim/serverEconomy.ts`) with `applyCommand` and compares `economyHash`; corrections carry the server's economy. Results the server makes (attack loot and spent troops, raid losses, gifts, chests) go through `applyServerResult` inside the request's transaction, with ledger lines. A village on the server is the raid base; uploads are ignored. Never re-run a battle the request already simulated: pass `known` to `battleEnd` / `remoteGroveBattleEnd` and `fallen` to `applyDefense`. Attacks, war attacks, war chests and donations settle server-held villages inside the same `Repo.transaction` as the result (`tests/backend/server/attacks-economy.test.ts`). Villages that stay on the device remain trusted-local (legality checks only); loot they upload is marked in the ledger when a server-held attacker takes it.
- Database changes are numbered files in `server/migrations/` (`0002_what_it_does.sql`), applied by `npm run server:migrate` as a release step (`server/migrate.ts`: checksums, an advisory lock, one transaction per file). The server refuses to start with pending migrations unless `MIGRATE_ON_BOOT=1`. Never edit an applied file; add a new one, and keep each change backward compatible with the previous server build (rolling deploys).
- Re-simulation runs in worker threads (step 57, `server/resim/`): `ctx.resim.run(engine, …)` → `{ result, fallen }`; `RESIM_WORKERS` (default cores − 1, 0 = main thread), `RESIM_QUEUE`; a full queue or failed worker answers `503 busy` (the game retries). Tests and tools use `InlineResimulator`. A new kind of battle must go through `resimulate` (never `runBattle` on the request thread).
- The server re-simulates every attack with `runBattle`; `npm run server:bench` (`server/bench.ts`) times it per Keep (step 18: 5 ms at Keep 1, up to ~0.45 s at Keeps 8–15 on a 2.1 GHz vCPU, which blocks the event loop; a worker pool is step 57). Never re-simulate the same battle twice in one request. Smoke charges come from the army (`smokeCharges`), so no new stored fields are needed. The server applies the loot penalty once. The client must not apply it again.
- **Honesty rule:** when nobody fits, the server sends a generated base with `opponent.kind: 'bot'`; the client labels it. Simulated raids are flagged `simulated: true`.
- Internal names stay stable (`grove`, `toadstool-kingdoms` in `/v1/hello`). See `docs/rebuild/ID_MAP.md`.

## Monetization and compliance (keep these rules)

- Payments go through `PaymentProvider`: mock (testing sandbox only), StoreKit 2 (iOS, `ios/App/App/TkStorePlugin.swift`), Play Billing (Android, `TkBillingPlugin.java`, **off unless the build sets `VITE_PLAY_BILLING=1`**: the owner turns it on). Public web purchases stay disabled; ask the owner before adding a web payment path.
- Real prices only in the Store and its confirm step. Clear confirm on every purchase (FTC/Epic lesson). Under-18 spending cap. Chat filter on.
- Paid random items need their odds shown before purchase (App Review 3.1.1), and the loot-box laws in each market must be checked first. The daily chest is free and never sold. Streak repairs, ability charges and trial rewards are never sold.
- New app identity: the display name is "Kagemura". The bundle id is still `com.toadstoolkingdoms.app` (a new one means a new App Store / Play listing: owner steps in `docs/SHIPPING.md`). Store product ids come from `store.json` `storeProductIds` (the game's own ids never change).
